# DynamicRouteLab — Methodology

This document states what the platform measures, how it measures it, what it assumes, and what it
cannot show. It is written to be checked against the code: every claim below has a corresponding
module or test, referenced in brackets.

## 1. Research question and hypotheses

Comparing Dijkstra's algorithm, A* Search, and Bellman–Ford on identical snapshots of a dynamic
road network, under congestion and closures:

- **H1.** A* with an admissible heuristic expands fewer vertices than Dijkstra on at least some
  source–destination pairs, while returning the same optimal cost.
- **H2.** Relative performance depends on topology, heuristic quality, and graph size.
- **H3.** Traffic updates can change the optimal route even when the optimal cost is unchanged
  (equal-cost alternatives).
- **H4.** Repeated full recomputation after several updates has a measurable computational cost.

These are hypotheses. The platform reports the evidence needed to accept, reject, or qualify each.
It does not declare any of them confirmed. Results from a small number of synthetic graphs support
statements only about those graphs.

## 2. Data: synthetic graphs only

- **Topology.** An n × n grid of intersections with IDs `r_c`. Roads connect 4-neighbours
  (`grid`). Optional `grid_diagonal` adds one diagonal per cell (random orientation) and
  `random_extra` adds long-range roads of Chebyshev reach ≤ 2 with probability 0.12 per cell.
- **Weights.** Integer travel-time units drawn uniformly from `[weight_min, weight_max]`
  (default 2–12) by `random.Random(seed)`. Weights are non-negative.
- **Coordinates.** Grid coordinates only, used for the layout and the heuristic. They are not
  geographic. No real street network or traffic feed is used. [`server/graph/generator.py`]
- **Reproducibility.** Same `(n, seed, topology, weight range)` yields the same graph.

## 3. Traffic model (simulated, not live)

- **Congestion.** A seeded sample of `congestion_pct` % of open roads (at least one) is multiplied
  by `congestion_factor` (≥ 1). The multiplier applies to the road's **original** weight, so
  repeated application does not compound. [`server/graph/traffic.py`]
- **Closure.** A closed road is excluded from the adjacency used by all three algorithms and from
  the A* heuristic scale. It is therefore unavailable to all algorithms consistently.
- **Manual edits.** A weight can be set to any finite non-negative value. The original weight is kept.
- **Experiment draws.** Congestion draw *k* uses seed `seed + 9999 + k`
  (`CONGESTION_SEED_OFFSET`). The interactive simulator uses draw 0, so it matches the
  experiment's first update.

## 4. Algorithms

| Algorithm | Implementation | Processing count (algorithm-specific) |
|---|---|---|
| Dijkstra | Binary-heap priority queue, lazy deletion, settled set, early exit at target. Non-negative weights. [`algorithms/dijkstra.py`] | **settled vertices** |
| A* Search | Same heap with f = g + h. Heuristic below. Early exit at target. [`algorithms/astar.py`] | **expanded vertices** |
| Bellman–Ford | Edge-list relaxation over both directions of each road, early exit when a pass changes nothing, one extra scan for negative-cycle detection. [`algorithms/bellman_ford.py`] | **relaxation passes** |

**Edge relaxations** are counted for every algorithm as examinations of a directed edge (u → v)
during the search, each one a tentative-distance comparison. It is the cross-algorithm work counter. It is still an
implementation-dependent count, and it does not capture memory access or heap-operation cost.

**Negative weights.** Bellman–Ford supports negative weights and detects negative cycles. The road
model uses non-negative travel times, so negative weights are never generated by the platform.
They are not physically meaningful travel times here. The only negative inputs are used in unit
tests.

### 4.1 A* heuristic

For a road *e* = (u, v), let `L(e)` be the Manhattan length of its endpoints' grid coordinates
(1 on a plain grid, 2–4 for diagonal and long-range roads). Define

    c* = min over open roads e of  w(e) / L(e)
    h(v) = c* · Manhattan(v, target)

**Admissibility.** Each road satisfies w(e) ≥ c* · L(e). Along any path from v to the target, the
Manhattan lengths sum to at least Manhattan(v, target) by the triangle inequality. So every path
costs at least h(v).

**Consistency.** h(u) ≤ c* · L(u, v) + h(v) ≤ w(u, v) + h(v) for every road (u, v).

**Traffic.** c* is recomputed from current weights and open roads on every call, so the bound stays
valid after congestion and closures. It is computed inside the timed region because it is part of
A*'s work.

**Correction note.** An earlier version used `Manhattan × min_edge_weight`. That bound is only valid
when every road has L(e) = 1. On `grid_diagonal` and `random_extra` graphs it overestimated the
remaining cost. In an ad hoc development sweep (not committed; 2 topologies × 60 seeds × 3 weight ranges × 3
endpoint pairs, n = 7; 1080 cases), the earlier version returned a non-optimal cost in 103 cases.
The per-road bound above returned 0 mismatches. Regression tests now check admissibility, consistency, and cost equality against
Dijkstra on all three topologies after congestion and closures. [`tests/test_algorithms.py`]

## 5. Correctness validation

Every algorithm result, in every snapshot and every timed trial, is checked against:

1. **Reference cost.** An independent Dijkstra reference (`algorithms/reference.py`) gives the
   trusted optimal cost. The check passes when costs agree within 1e-6, or when both report
   unreachable.
2. **Path validity.** The path starts at the source and ends at the destination. Each consecutive
   pair is an open road in the snapshot. The cost recomputed by summing road weights equals the
   reported cost within 1e-6. Failed searches must report no path. [`benchmark._check_path`]
3. **Same graph version.** All algorithms in a snapshot receive one adjacency built once from one
   payload. The experiment output records the snapshot seed and affected-road IDs.

Status is `pass` only if both checks pass. The UI and exports show the status for each algorithm.

## 6. Benchmark design

- **Timing boundary.** Only the call to an algorithm function is timed, with
  `time.perf_counter_ns()` (monotonic). Graph generation, traffic application, reference checks,
  serialisation, and rendering are outside the timed region. Each timed sample is one call.
- **Warm-up.** One untimed call per algorithm before the timed trials.
- **Ordering.** Trials alternate across algorithms (Dijkstra, A*, Bellman–Ford, Dijkstra, …) so
  host drift affects all three roughly equally.
- **Statistics.** Median (primary), mean, sample standard deviation, min, max, and coefficient of
  variation of runtime. Processing and relaxation counts are reported as medians, and
  `counts_consistent` confirms they did not change across trials.
- **Route-change frequency.** Across `updates` congestion draws, the fraction of draws where the
  Dijkstra route differs from the baseline route. Dijkstra is the canonical route because it is
  deterministic. Other algorithms may return a different equal-cost route. Each update also records
  whether the route changed while the cost stayed the same (H3 evidence).
- **Recomputation cost (H4).** The sum of the three algorithms' median runtimes per update, summed
  over updates.
- **Environment.** Python version, platform, machine, FastAPI and uvicorn versions, timer, and
  timing boundary are recorded in every experiment export.

### Limitations of timing

- Measurements are wall-clock on a shared sandbox. They are noisy, and they depend on CPU
  frequency, scheduling, Python version, and garbage collection. Use the median, the variability
  columns, and repeated experiments, not one number.
- Python interpreter overhead dominates these small graphs. Runtime rankings on this platform
  say little about compiled implementations.
- Small graphs (n ≤ 6) have sub-millisecond runtimes that are close to timer resolution.

## 7. Reproducibility

Each export (`JSON` and `CSV`) includes the configuration, seed, source and target, congestion
settings, timestamp (ISO-8601, UTC), software and environment information, and the affected road
IDs. Given the same configuration:

- graph, path, cost, processing counts, relaxations, route-change results, and correctness
  status are identical (tested: `test_experiment_counts_and_costs_are_reproducible_for_same_config`);
- only timing fields differ between runs.

`examples/sample_experiment.json` gives a sample configuration. It is labelled as sample data and
contains no measurements.

## 8. Scope and honest limitations

- No live traffic provider is integrated. All traffic is simulated on synthetic graphs.
- Results are for the tested synthetic graphs only. They do not generalise to real road networks
  without further testing.
- The platform does not compute statistical significance tests. Medians and spreads are
  descriptive. Any claim of a performance difference needs a separate analysis of many seeds and
  graph sizes.
- Edge relaxations and processing counts are implementation-specific. Compare them with that in mind.
- The interactive lab runs one execution per algorithm per click. Single executions are noisy and
  are not used for performance claims. Use the Experiment Runner.
- Concurrency: the API is stateless. Each request carries its graph. Long experiments block one
  request, and the UI disables the run button and shows progress while they run.
- Bellman–Ford pass counts depend on edge ordering. Its work is not directly comparable to the
  vertex counts of Dijkstra and A*.
